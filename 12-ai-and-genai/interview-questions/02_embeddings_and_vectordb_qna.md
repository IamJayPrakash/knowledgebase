# AI & GenAI Interview Questions: Part 2 — Embeddings & Vector Databases (Q21 - Q40)

---

### Q21: What is a dense vector embedding and how is it generated from raw text?
- **Answer**: A dense vector embedding is a continuous, fixed-dimensional floating-point array (e.g., 768 or 1536 dimensions) where semantic meaning is mapped geometrically. It is generated by passing tokenized text through an encoder model (e.g. BERT or modern text-embedding models) and extracting the contextualized activations from the final layer—typically via mean pooling over all token tokens or extracting the `[CLS]` token embedding.

### Q22: When should you use Cosine Similarity versus Euclidean ($L_2$) Distance versus Dot Product?
- **Answer**:
  - **Cosine Similarity**: Use when document length varies widely. It measures angular direction ($\cos \theta$), ignoring vector magnitudes.
  - **Dot Product**: Fastest calculation. When embeddings are $L_2$-normalized ($\|A\|=\|B\|=1$), Dot Product is mathematically equivalent to Cosine Similarity.
  - **Euclidean ($L_2$)**: Use when vector magnitude carries critical semantic significance (e.g. in spatial coordinates or clustering algorithms like $K$-Means).

### Q23: Why do we $L_2$-normalize embeddings before storing them in vector databases?
- **Answer**: $L_2$ normalization scales every vector to a unit length of 1.0 ($\sum v_i^2 = 1$). This allows vector database engines to replace computationally expensive cosine calculations (which require calculating norms and square roots on the fly) with pure hardware-accelerated Dot Product operations (MIPS), reducing query latency by up to 40%.

### Q24: Explain the internal architecture of HNSW (Hierarchical Navigable Small World).
- **Answer**: HNSW is a multi-layer graph index modeled on the skip-list data structure. The top layer contains a sparse graph with long-range edges connecting distant clusters for fast global navigation. Lower layers contain progressively denser graphs. At query time, search enters at the top layer, performs greedy routing to find the nearest local entry point, drops to the layer below, and repeats down to Layer 0, where a dense beam search identifies the top-$K$ nearest neighbors in $O(\log N)$ time.

### Q25: What is the role of hyperparameters $M$, $efConstruction$, and $efSearch$ in HNSW?
- **Answer**:
  - **$M$**: Maximum number of bidirectional links connected to each node. Higher $M$ increases recall accuracy and graph resilience, but increases RAM footprint and index build time.
  - **$efConstruction$**: Candidate priority queue size during graph construction. Higher values produce superior graph connectivity at the expense of slower indexing.
  - **$efSearch$**: Size of the dynamic candidate list evaluated at query time. Can be tuned dynamically per query: higher $efSearch$ boosts recall for critical queries at the cost of higher latency.

### Q26: What is IVF-PQ (Inverted File with Product Quantization) and when is it preferred over HNSW?
- **Answer**: IVF-PQ partitions the vector space into $K$ Voronoi cells (Inverted File) and compresses high-dimensional vectors by slicing them into sub-vectors and mapping each to the nearest cluster centroid in a codebook (Product Quantization). IVF-PQ is preferred over HNSW when RAM is severely constrained for massive billion-scale vector datasets, as it compresses memory consumption by 80–95%, albeit with lower recall.

### Q27: What is Matryoshka Representation Learning (MRL)?
- **Answer**: MRL (used in OpenAI's `text-embedding-3` models) trains embedding vectors such that the most critical, high-variance semantic information is concentrated in the earliest dimensions. This allows developers to truncate a 1536-dimensional vector down to 512 or 256 dimensions simply by slicing the array (`vector[:256]`) and re-normalizing, reducing vector database storage and RAM costs by up to 66% with negligible degradation in search recall.

### Q28: Explain the difference between Pre-Filtering and Post-Filtering in vector databases.
- **Answer**:
  - **Post-Filtering**: Runs the ANN vector search first across the entire database to retrieve the top-$K$ nearest neighbors, then applies metadata filters (e.g., `WHERE tenant_id = 'XYZ'`). If the metadata filter is highly selective, all top-$K$ vector results may be discarded, resulting in empty returns.
  - **Pre-Filtering / Iterative Single-Stage Filtering**: The metadata filter is evaluated *during* graph traversal. Only nodes satisfying the metadata criteria are explored, guaranteeing that all returned candidates are valid.

### Q29: What are the architectural differences between ChromaDB, Pinecone, Qdrant, and Milvus?
- **Answer**:
  - **ChromaDB**: Lightweight, embedded, runs in-process (like SQLite). Ideal for rapid local prototyping and test suites.
  - **Qdrant**: Written in Rust, highly performant, features native payload filtering and on-disk payload storage for memory efficiency.
  - **Pinecone**: Fully managed, proprietary serverless cloud vector database with automated scaling and zero DevOps overhead.
  - **Milvus**: Distributed, cloud-native architecture written in Go/C++ with separate compute and storage layers, engineered for massive multi-billion vector enterprise deployments.

### Q30: What is the "Curse of Dimensionality" in high-dimensional vector search?
- **Answer**: In high-dimensional spaces ($D > 1000$), the volume of space grows exponentially, causing data points to become extremely sparse. Geometrically, the distance between the closest point and the farthest point converges toward parity ($d_{\max} \approx d_{\min}$), making distance metrics noisy and requiring specialized graph topologies (HNSW) to achieve meaningful clustering.

### Q31: How do you handle multi-tenancy securely in vector databases?
- **Answer**:
  - **Namespace / Collection Isolation**: Create dedicated isolated collections per tenant. Complete physical isolation, but higher resource overhead per tenant.
  - **Metadata Payload Filtering**: Store all vectors in a shared collection, attaching a mandatory `tenant_id` field to every vector payload, enforced by single-stage pre-filtering at the database proxy layer.

### Q32: What is Maximum Marginal Relevance (MMR) and why is it used in retrieval?
- **Answer**: MMR balances relevance with diversity to eliminate redundancy in retrieved contexts. It selects candidates by optimizing:
  $$\text{MMR} = \arg\max_{d_i \in R \setminus S} \left[ \lambda \cdot \text{Sim}(d_i, q) - (1 - \lambda) \max_{d_j \in S} \text{Sim}(d_i, d_j) \right]$$
  Where $\lambda$ trades off similarity to the query against similarity to already selected documents $S$, preventing 5 identical chunks from saturating the context window.

### Q33: How does vector indexing handle real-time CRUD operations (inserts, updates, deletes)?
- **Answer**: HNSW graphs are notoriously difficult to update dynamically because deleting a node leaves orphan edges. Production vector DBs use **Tombstoning** (marking deleted vectors in a bitset so search ignores them) paired with background **Compaction jobs** that periodically rebuild affected subgraphs. Newly inserted vectors are buffered in a fast in-memory mutable index and merged into the immutable disk segment via an LSM-style pipeline.

### Q34: What is Sparse-Dense Hybrid representation in models like SPLADE?
- **Answer**: SPLADE (Sparse Lexical and Anonymized Dense) predicts expansion terms over the model's vocabulary, generating a high-dimensional sparse vector (30,000+ dimensions) where only matching or conceptually related terms have non-zero weights. It unifies the exact keyword precision of BM25 with deep semantic expansion in a single indexable sparse vector.

### Q35: What is the difference between asymmetric and symmetric search in embedding models?
- **Answer**:
  - **Symmetric Search**: Query and Document are of comparable length and type (e.g., finding similar questions on StackOverflow).
  - **Asymmetric Search**: Query is short and interrogative (e.g. 5 words), while documents are long paragraphs (e.g. 300 words). Asymmetric models (like BGE, E5) use instruction prefixes (`"query: ..."` vs `"passage: ..."`) to bridge this semantic gap.

### Q36: How does vector quantization affect search latency and precision?
- **Answer**: Scalar Quantization (SQ8) converts 32-bit floats into 8-bit integers, reducing memory footprint by 75% and accelerating distance math using SIMD/AVX2 instructions with less than 1% loss in recall. Product Quantization (PQ) provides even higher compression (90%+), but introduces lossy approximations that require second-stage re-scoring against original vectors.

### Q37: How do you choose the optimal embedding chunk size for enterprise documents?
- **Answer**:
  - **Small Chunks (100–250 tokens)**: High semantic granularity and precision for targeted Q&A; ideal for first-stage vector search.
  - **Large Chunks (500–1000 tokens)**: Rich surrounding context and cohesive reasoning; ideal for summarization.
  - **Best Practice**: Use Small-to-Big (Parent-Document) chunking: index small child chunks for vector search, but retrieve the larger parent chunk for generation.

### Q38: What is the purpose of the Annoy (Approximate Nearest Neighbors Oh Yeah) index?
- **Answer**: Developed by Spotify, Annoy builds a forest of randomized binary search trees by repeatedly bisecting vector space with random hyperplanes. It is read-only, disk-backed, and allows memory-mapping (`mmap`) across processes, making it ideal for high-throughput, low-memory static recommendation serving.

### Q39: Can you perform vector similarity search inside standard relational databases like PostgreSQL?
- **Answer**: Yes, via the `pgvector` extension. It supports HNSW and IVFFlat indexing natively within PostgreSQL tables, allowing developers to combine relational SQL joins (`JOIN orders ON ...`) and vector similarity queries (`ORDER BY embedding <=> query_vector LIMIT 5`) in a single ACID-compliant database transaction.

### Q40: What metrics are used to benchmark vector search performance?
- **Answer**:
  - **Recall@K**: Percentage of true nearest neighbors retrieved compared to exact brute-force $k$-NN.
  - **QPS (Queries Per Second)**: Search throughput under concurrent load.
  - **Latency (P50, P95, P99)**: Milliseconds required to return top-$K$ candidates.
  - **Index Build Time & Index Size**: GPU/CPU hours to construct the graph and total RAM/disk consumption in gigabytes.
